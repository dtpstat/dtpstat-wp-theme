# Обновление WordPress-темы (без переустановки сайта)

**Единственная точка входа в деплой темы и её конфигурации — `bin/deploy.sh`.**
Скрипт запускается на **самом сервере WordPress**, а не с рабочей станции через
`rsync --delete`. Он не обновляет БД, записи и медиа и не запускает
`bin/install.sh`.

При новой установке используйте [INSTALLER.md](INSTALLER.md):
`bin/install.sh` уже сам генерирует PHP-константы.

## Структура

- `<repo>/.env` — настройки проекта; Git игнорирует этот файл.
- `bin/deploy.sh` → `bin/deploy.py` — проверка и весь процесс деплоя.
- `bin/generate-config.py` — **внутренний** генератор PHP-констант; запускается
  автоматически из `deploy.py` и `install.py`.
- `WP_CONTENT_DIR/dtpstat-config.php` — результат генерации.
- `WP_CONTENT_DIR/dtpstat-releases/dtpstat-child-<hash>/` — отдельные неизменяемые
  версии темы.
- `WP_CONTENT_DIR/themes/dtpstat-child` — символическая ссылка на выбранный
  релиз.

После перехода на релизы `git fetch`, `git pull` и изменение исходников
репозитория **не меняют активную тему WordPress**. Версию переключает только
`deploy.sh`.

## Запуск на сервере

Рабочая директория — нужный Git checkout/worktree с проверенными исходниками.
Для WordPress в `/var/www/wp`:

```bash
cd /var/www/dtpstat-wp-theme

# Прежде всего проверить без изменения сайта и конфигурации:
bash bin/deploy.sh --wp-path /var/www/wp --check

# После успешных тестов и одобрения развёртывания:
bash bin/deploy.sh --wp-path /var/www/wp
```

По умолчанию `.env` ищется в **корне именно запускаемой копии репозитория**.
При работе из временного worktree с подготовленным .env основного проекта
укажите его явно:

```bash
bash bin/deploy.sh \
  --wp-path /var/www/wp \
  --env-file /var/www/dtpstat-wp-theme/.env \
  --check
```

Сначала проверяйте тот же `--env-file` и `--wp-path`, которые будут
использоваться при применении. Не копируйте файл руками в `wp-content`.

### Что проверяет `--check`

- Наличие установленного WordPress и корректного каталога `wp-content`;
- доступ на запись к конфигурации и папке релизов;
- наличие и содержимое проектного `.env`, все обязательные адреса и их формат;
- PHP-синтаксис всех PHP-файлов исходной темы;
- отсутствие опасных символических ссылок внутри исходной темы;
- допустимость текущего типа каталога активной темы;
- неизменность существующего релиза, если хеш уже совпадает.

**Режим проверки ничего не создаёт и не меняет на сайте.**

### ВНИМАНИЕ: реальный деплой меняет работающий сайт

После успешной проверки обычный запуск:

1. Копирует исходники темы в отдельный релиз; активная тема пока не затронута.
2. Формирует `dtpstat-config.php` из `.env` атомарной заменой.
3. Атомарно переключает ссылку `themes/dtpstat-child` на новую версию
   (когда прежняя тема уже подключена символической ссылкой).
4. Выводит путь прежней версии для возможного ручного отката.

Прежний релиз сохраняется; нет `rsync --delete`, удаления пользовательских
файлов или перезаписи исходного Git-репозитория. При ошибке переключения
deploy **пытается** восстановить прежний сгенерированный PHP-конфиг и
ранее перемещённый каталог темы, но **полноценного автоматического отката
работающего сайта нет**. Сброс OPcache также не выполняется.
При необходимости управляйте кэшами отдельно, после проверки HTTP-сайта.

### Если тема — обычный каталог, а не символическая ссылка

Без специального разрешения деплой **откажется его заменять**.
Для миграции обычного каталога в релизную схему предусмотрен
`--adopt-existing-directory`:

```bash
# Сначала dry-run:
bash bin/deploy.sh --wp-path /var/www/wp \
  --adopt-existing-directory --check
```

**ВНИМАНИЕ: реальное применение `--adopt-existing-directory` прерывает
обычную файловую структуру работающей темы на короткий момент.**
Сначала отдельно проверьте резервную копию, права и план восстановления.
При применении прежний каталог перемещается в `dtpstat-releases/legacy-*`,
а вместо него создаётся ссылка. Скрипт пытается восстановить каталог, если
последнее переключение завершилось ошибкой, но не гарантирует откат после
системного сбоя. Не используйте этот флаг для текущего сервера, где тема
уже подключена symlink.

## После выкладки

Проверьте домашнюю страницу с картой, `/dtp/<id>/`, футер, загрузку
шрифтов и CSS, а также логи PHP. При необходимости очистите HTML/CDN-кэш.
В некоторых конфигурациях OPcache может понадобиться явная инвалидация;
перезапуск сервисов скрипт не делает.

Статические тесты репозитория:

```bash
python3 -m unittest discover -s tests -v
```

  **оба равны `https://fe.dtp-stat.ru`**. Прежнее `fp.dtp-stat.ru`

- PHP-файл `/var/www/wp/wp-content/dtpstat-config.php` был создан
  самим `deploy`. WordPress успешно прочитал обе константы.
- Активная тема переключена с изменяемой Git-ссылки на релиз
  `wp-content/dtpstat-releases/dtpstat-child-3f550d1759f3b9f5ada0`.
- Проверены 53 теста, `deploy --check`, WP-CLI и ответы HTTP 200
  главной и `/dtp/1/`. **Это не заменяет визуальную проверку карты,
  браузерного JS, футера и ошибок PHP.**

Для следующих обновлений из основного checkout, когда текущая тема
уже ссылается на релиз:

```bash
cd /var/www/dtpstat-wp-theme
git status --short
git fetch origin
git pull --ff-only origin main

# dry-run: проверяет версию, PHP-синтаксис и PHP-конфиг
bash bin/deploy.sh --wp-path /var/www/wp --check

# ВНИМАНИЕ: следующая команда публикует новую тему/конфигурацию.
# Применять только после тестов, проверки резервной копии и плана отката:
bash bin/deploy.sh --wp-path /var/www/wp
```

`git pull` сам по себе не публикует тему, если текущая ссылка осталась
в `dtpstat-releases/`. Не используйте `install.sh` для обычных обновлений.

### Проверка без изменения сайта

```bash
cd /var/www/dtpstat-wp-theme
php wp-cli.phar --path=/var/www/wp eval '
printf("MAP=%s\\n", dtp_map_url());
printf("FRONTEND=%s\\n", dtp_pages_url());
printf("EMAIL=%s\\n", dtp_config("DTP_CONTACT_EMAIL"));
printf("THEME=%s\\n", get_stylesheet());
'

readlink -f /var/www/wp/wp-content/themes/dtpstat-child
curl -fsS -o /dev/null -w 'Homepage: HTTP %{http_code}\\n' https://wp.dtp-stat.ru/
curl -fsS -o /dev/null -w 'DTP page: HTTP %{http_code}\\n' https://wp.dtp-stat.ru/dtp/1/
```

Для проверки самой карты нужно просмотреть **фактический HTML и iframe**,
а не только HTTP-статус:

```bash
curl -fsSL https://wp.dtp-stat.ru/ | grep -oE '<iframe[^>]*>' | head -n 3
```

В iframe главной ожидается адрес `https://fe.dtp-stat.ru/` (или
эквивалентный); в `/dtp/1/` — адрес страницы деталей фронтенда.
Проверьте также логи PHP, загрузку CSS, шрифтов и внешних API.
Скрипт не сбрасывает кэши HTML, CDN и OPcache.

### ВНИМАНИЕ: откат меняет работающий сайт

До каждого нового деплоя запишите:

- текущую цель `readlink -f /var/www/wp/wp-content/themes/dtpstat-child`;
- копию `wp-content/dtpstat-config.php` с защищёнными правами;
- путь проверенной резервной копии файлов темы и, при установке,
  резервной копии WordPress/БД.

При ошибке **не запускайте повторный `install`** и не удаляйте файлы.
Чтобы вернуться к предыдущей версии, необходимо атомарно переключить
`wp-content/themes/dtpstat-child` на сохранённый прежний релиз/каталог
и при изменении настроек восстановить соответствующую сохранённую версию
`dtpstat-config.php`. Это операция над работающей темой; выполняйте её
только после проверки обоих путей и резервной копии. Не используйте
`rsync --delete` или `git reset --hard` как способ отката продакшена.

### Уборка локальных временных файлов

После **фактической** проверки сайта можно убрать вспомогательный
worktree `$HOME/dtpstat-release-7ef0c5f`: скопированная тема уже
работает из `wp-content/dtpstat-releases/`. Сначала убедитесь,
что исходники этого worktree не используются никакой активной ссылкой,
и что в нём нет локальных изменений.

```bash
git -C /var/www/dtpstat-wp-theme worktree list
git -C "$HOME/dtpstat-release-7ef0c5f" status --short
readlink -f /var/www/wp/wp-content/themes/dtpstat-child
```

**ВНИМАНИЕ: удаление worktree необратимо для его незакоммиченных файлов.**
После проверки чистоты и независимости активной темы допускается:
`git -C /var/www/dtpstat-wp-theme worktree remove
"$HOME/dtpstat-release-7ef0c5f"` (одной командой в терминале).
Не используйте `rm -rf` для удаления Git worktree: это оставляет
устаревшие служебные записи.

**Не удаляйте** подтверждённую резервную копию перед миграцией,
активный `dtpstat-releases/dtpstat-child-*`,
прежние релизы, необходимые для отката, или проектный `.env`.
Удаление старых релизов должно быть отдельной процедурой после
проверки точек отката.

## Удалённый запуск

Ранее `bin/deploy.sh` без аргументов выполнял `rsync --delete` через
SSH на жёстко заданный хост. **Этот режим заменён.** Для управления
удалённым сервером запустите новый `bin/deploy.sh` через SSH
на том сервере, где находится WordPress и проектный `.env`.
Нельзя применять прежнюю команду из документации с удалённым `rsync`
к символической ссылке работающей темы.

Ручной запуск `bin/generate-config.py` нужен только для диагностики или
нестандартной инфраструктуры и **не является штатным шагом деплоя**.
