# Обновление WordPress-темы (без переустановки сайта)

**Единственная точка входа в деплой темы и её конфигурации — `bin/deploy.sh`.**
Скрипт запускается на **самом сервере WordPress**, а не с рабочей станции через
`rsync --delete`. Он не обновляет БД, записи и медиа и не запускает
`bin/install.sh`.

При новой установке используйте [INSTALLER.md](INSTALLER.md):
`bin/install.sh` уже сам генерирует PHP-константы.

## Структура

- `<repo>/.env` — настройки проекта; Git игнорирует этот файл.
- `bin/deploy.sh` → `bin/deploy.py` — проверка и весь процесс деплоя.
- `bin/generate-config.py` — **внутренний** генератор PHP-констант; запускается
  автоматически из `deploy.py` и `install.py`.
- `WP_CONTENT_DIR/dtpstat-config.php` — результат генерации.
- `WP_CONTENT_DIR/dtpstat-releases/dtpstat-child-<hash>/` — отдельные неизменяемые
  версии темы.
- `WP_CONTENT_DIR/themes/dtpstat-child` — символическая ссылка на выбранный
  релиз.

После перехода на релизы `git fetch`, `git pull` и изменение исходников
репозитория **не меняют активную тему WordPress**. Версию переключает только
`deploy.sh`.

## Запуск на сервере

Рабочая директория — нужный Git checkout/worktree с проверенными исходниками.
Для WordPress в `/var/www/wp`:

```bash
cd /var/www/dtpstat-wp-theme

# Прежде всего проверить без изменения сайта и конфигурации:
bash bin/deploy.sh --wp-path /var/www/wp --check

# После успешных тестов и одобрения развёртывания:
bash bin/deploy.sh --wp-path /var/www/wp
```

По умолчанию `.env` ищется в **корне именно запускаемой копии репозитория**.
При работе из временного worktree с подготовленным .env основного проекта
укажите его явно:

```bash
bash bin/deploy.sh \
  --wp-path /var/www/wp \
  --env-file /var/www/dtpstat-wp-theme/.env \
  --check
```

Сначала проверяйте тот же `--env-file` и `--wp-path`, которые будут
использоваться при применении. Не копируйте файл руками в `wp-content`.

### Что проверяет `--check`

- Наличие установленного WordPress и корректного каталога `wp-content`;
- доступ на запись к конфигурации и папке релизов;
- наличие и содержимое проектного `.env`, все обязательные адреса и их формат;
- PHP-синтаксис всех PHP-файлов исходной темы;
- отсутствие опасных символических ссылок внутри исходной темы;
- допустимость текущего типа каталога активной темы;
- неизменность существующего релиза, если хеш уже совпадает.

**Режим проверки ничего не создаёт и не меняет на сайте.**

### ВНИМАНИЕ: реальный деплой меняет работающий сайт

После успешной проверки обычный запуск:

1. Копирует исходники темы в отдельный релиз; активная тема пока не затронута.
2. Формирует `dtpstat-config.php` из `.env` атомарной заменой.
3. Атомарно переключает ссылку `themes/dtpstat-child` на новую версию
   (когда прежняя тема уже подключена символической ссылкой).
4. Выводит путь прежней версии для возможного ручного отката.

Прежний релиз сохраняется; нет `rsync --delete`, удаления пользовательских
файлов или перезаписи исходного Git-репозитория. **Автоматический откат и
сброс OPcache не выполняются.** При необходимости управляйте кэшами отдельно,
после проверки HTTP-сайта.

### Если тема — обычный каталог, а не символическая ссылка

Без специального разрешения деплой **откажется его заменять**.
Для миграции обычного каталога в релизную схему предусмотрен
`--adopt-existing-directory`:

```bash
# Сначала dry-run:
bash bin/deploy.sh --wp-path /var/www/wp \
  --adopt-existing-directory --check
```

**ВНИМАНИЕ: реальное применение `--adopt-existing-directory` прерывает
обычную файловую структуру работающей темы на короткий момент.**
Сначала отдельно проверьте резервную копию, права и план восстановления.
При применении прежний каталог перемещается в `dtpstat-releases/legacy-*`,
а вместо него создаётся ссылка. Скрипт пытается восстановить каталог, если
последнее переключение завершилось ошибкой, но не гарантирует откат после
системного сбоя. Не используйте этот флаг для текущего сервера, где тема
уже подключена symlink.

## После выкладки

Проверьте домашнюю страницу с картой, `/dtp/<id>/`, футер, загрузку
шрифтов и CSS, а также логи PHP. При необходимости очистите HTML/CDN-кэш.
В некоторых конфигурациях OPcache может понадобиться явная инвалидация;
перезапуск сервисов скрипт не делает.

Статические тесты репозитория:

```bash
python3 -m unittest discover -s tests -v
```

## Удалённый запуск

Ранее `bin/deploy.sh` без аргументов выполнял `rsync --delete` через
SSH на жёстко заданный хост. **Этот режим заменён.** Для управления
удалённым сервером запустите новый `bin/deploy.sh` через SSH
на том сервере, где находится WordPress и проектный `.env`.
Нельзя применять прежнюю команду из документации с удалённым `rsync`
к символической ссылке работающей темы.

Ручной запуск `bin/generate-config.py` нужен только для диагностики или
нестандартной инфраструктуры и **не является штатным шагом деплоя**.
