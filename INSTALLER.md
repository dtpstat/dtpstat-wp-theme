# Серверный установщик пакета DTPStat

Это основная инструкция для установщика, который **уже находится в репозитории**:
`bin/install.sh` запускает `bin/install.py`, а операции внутри WordPress
выполняет `bin/install-wp.php` через WP-CLI. Целевая установка — **локальный,
уже установленный одиночный WordPress**; Docker Compose и установка ядра в этот
сценарий не входят.

В пакете также остались отдельные инструменты прежнего стенда:
`bin/export.sh` (экспорт через `bin/attachments.php dump`),
`bin/verify.sh` и `compose.yml`. Не путайте их с новым установщиком.
Краткая инструкция и карта документации находятся в [README.md](README.md).

## Первый запуск: проверка

### Замена существующего содержимого

Для развёртывания пакета поверх существующего сайта используйте `--replace-content`:

```bash
bash bin/install.sh --wp-path /var/www/wp --wp-cli-phar /var/www/dtpstat-wp-theme/wp-cli.phar --replace-content
```

Режим сначала делает резервную копию БД и wp-content. Затем удаляет ВСЕ записи
таблицы posts, включая страницы, посты/CPT, вложения, ревизии, блоковую навигацию,
шаблоны, глобальные стили и пункты меню. Связанные комментарии/meta удаляются
через API WordPress. Медиа удаляются через wp_delete_attachment вместе с их
файлами. Также очищаются классические меню, метки и категории, кроме обязательной
категории по умолчанию. Затем импортируется пакет. Пользователи, пароли,
wp-config.php и параметры подключения БД сохраняются. Это замена контента,
а не удаление БД; сторонние таблицы плагинов и прочие опции не сбрасываются.
Повторный запуск с этим ключом снова заменит контент после новой резервной копии.

Для просмотра плана без удаления добавьте `--check`. Блок `wp_navigation`
больше не останавливает проверку в режиме замены. Пустота цели проверяется
только без `--replace-content`.

От пользователя, владеющего файлами WordPress:

```bash
cd /var/www/dtpstat-wp-theme
bash bin/install.sh --wp-path /var/www/wp --check
```

Адрес берётся из текущей настройки `home`. Для явного адреса:

```bash
bash bin/install.sh --wp-path /var/www/wp --url https://wp.dtp-stat.ru --check
```

Это только предварительная проверка. Создаются журнал и внешняя блокировка,
но установщик не меняет файлы и записи сайта, не устанавливает ПО и не скачивает
плагины. Как и любой WP-CLI-вызов с загрузкой WP, он запускает обычный bootstrap
существующих плагинов. Их собственные побочные действия установщик не контролирует.

После успешной проверки установка запускается той же командой без `--check`.
Если на цели есть только штатные записи, предварительная проверка остановится
и предложит `--remove-stock-content`. Этот ключ явно разрешает удаление
`hello-world` (post), `sample-page` и `privacy-policy` (page), в том числе
если эти записи редактировались. Другой контент, занятые ID, повторный импорт
и восстановление после частичной установки не обходятся через `--force`.
Вместо обхода проверок используйте описанный выше режим `--replace-content`,
который сначала создаёт резервную копию и освобождает ID удалением контента.

## WP-CLI и зависимости

Нужны Bash, Python >= 3.8, PHP CLI с mysqli/json/libxml/SimpleXML/xml/zlib,
WP-CLI с командами import/db/theme/plugin и rsync. В самой дочерней теме
используются функции `str_starts_with()` и `str_contains()`, поэтому **PHP
веб-сервера должен быть не ниже 8.0**; при выполнении WP-CLI нужен совместимый
PHP CLI. Для БД нужен совместимый
с WP-CLI mysqldump или mariadb-dump. Скрипт проверяет наличие dump-команды;
совместимость с конкретным сервером БД проверяется реальным экспортом до
изменений сайта. PHP-бинарник и конфигурация должны подходить установленному WP.

WP-CLI в PATH:

```bash
bash bin/install.sh --wp-path /var/www/wp --wp-bin /usr/local/bin/wp --check
```

WP-CLI в PHAR (в данном репозитории файл `wp-cli.phar` лежит в корне):

```bash
bash bin/install.sh --wp-path /var/www/wp --wp-cli-phar /var/www/dtpstat-wp-theme/wp-cli.phar --check
```

Ключи принимают пути, а не строки команд. Нельзя передавать `php ~/wp-cli.phar`
в `--wp-bin`. Для осознанного запуска root нужен отдельный `--allow-root`;
предпочтителен владелец файлов WP. Пароль администратора и новые учётные записи
не нужны. Доступ к БД берётся WordPress из существующего `wp-config.php`.

## Что происходит при установке

1. Проверки пакета, WXR, наличия файлов медиа и кропов, пустоты цели, коллизий ID,
   администратора, версий, каталогов, прав и места для резервной копии.
2. Экспорт БД, копия всего wp-content и существующего `.htaccess`.
3. Удаление контента при --replace-content либо явно разрешённых стандартных записей,
   установка/активация ru_RU.
4. Neve и все экспортированные активные плагины с версиями из settings.json;
   копирование и активация dtpstat-child. Уже имеющиеся файлы этой темы обновляются.
5. Копирование uploads целиком без регенерации размеров и без удаления лишних файлов.
6. Восстановление медиа с исходными ID, полным набором meta из дампа и проверкой записи.
   Автор медиа назначается существующему администратору; исходные числовые ID авторов
   и post_parent не переносятся. Формат старого дампа хранит одно значение на meta-key,
   поэтому утраченные при экспорте повторные значения он восстановить не может.
7. Импорт WXR без attachment-элементов; авторы контента создаются импортёром.
8. home/siteurl, замена source_url в таблицах с префиксом текущего WP,
   настройки, категории, меню по locations из settings.json.
9. Реврайты, сброс кэша, проверка счётчиков, meta каждого вложения, настроек,
   категорий, пунктов и порядка меню. Временный импортёр удаляется только после успеха.

Проверяется наличие требуемых категорий, а не равенство общего количества:
штатная категория WP может оставаться дополнительно. Дополнительные файлы
существующей темы не удаляются. Это не точная файловая синхронизация с удалением.
При `--replace-content` уже установленные плагины из списка `settings.json`
могут быть перезаписаны указанными версиями посредством `wp plugin install --force`;
это следует учитывать при проверке совместимости стороннего окружения.

WordPress Importer, если его нет на сервере, устанавливается временно из
WordPress.org. Если версия есть в settings.json, применяется она; иначе
используется текущая доступная. Для воспроизводимого запуска задайте
`--importer-version ВЕРСИЯ`. Уже установленный импортёр сохраняется вместе
с исходным состоянием активации. Его версия этим ключом не меняется.

## Генерация PHP-констант при установке

Перед запуском настройте **проектный** `.env` (в корне данного репозитория),
взяв за основу [wordpress.env.example](wordpress.env.example).
Генератор `bin/generate-config.py` принимает только разрешённые ключи
`DTP_*`, проверяет обязательные `DTP_MAP_URL` и `DTP_FRONTEND_URL`,
контактный email и URL, исключает произвольный код и записывает только
публичные значения. Ни секреты, ни пароли в этот файл не помещайте.

`bin/install.sh --check` теперь **проверяет возможность генерации**
`WP_CONTENT_DIR/dtpstat-config.php`, не изменяя его. Для реальной
установки файл создаётся **после резервной копии wp-content**, до
активации дочерней темы WordPress. Если он уже существует, генератор
откажется перезаписать файл без своей метки происхождения.
При нестандартном расположении исходника используйте:

```bash
bash bin/install.sh --wp-path /var/www/wp \
  --env-file /path/to/project/.env --check
```

При обновлении **только темы** новый установщик повторно запускать
не нужно. Изменение настроек — отдельная безопасная команда:

```bash
python3 bin/generate-config.py \
  --env-file /path/to/project/.env \
  --output /var/www/wp/wp-content/dtpstat-config.php --check
# После проверки повторить без --check
```

`functions.php` загружает константы из этого PHP-файла один раз.
Источник `.env` не читается WordPress во время HTTP-запросов.
Экспортный WXR содержит `src="about:blank"` в iframe главной; тема
подставляет адрес карты из константы `DTP_MAP_URL` при отображении.
Для уже существующего контента в БД замена выполняется так же.

## Соответствие содержимого экспортного пакета

До запуска установщик проверяет соответствие **множеств ID** вложений в
`content/export.xml` и `content/attachments.json`, уникальность ID в JSON,
наличие основных файлов и файлов всех перечисленных размеров в `uploads`.
Элементы `attachment` из WXR перед передачей импортёру удаляются полностью.
В текущем исходном WXR встречаются повторные элементы с одинаковыми ID:
они не создают дополнительных вложений, поскольку не импортируются.
Это не означает, что WXR содержит больше **уникальных** медиа.

Для независимой проверки данных пакета без WordPress используйте:

```bash
python3 -m unittest discover -s tests -v
```

Проверки содержимого, синтаксиса и мок-тесты не подтверждают, что настоящий
`wp import` или установка плагинов завершатся успешно на целевом сервере.

## Журнал, время и ошибки

Каждая внешняя команда выводится, её stdout/stderr доступны в терминале и журнале.
Каждые 15 секунд долгой команды выводится сообщение, что она ещё выполняется.
Машинный JSON предварительной проверки разбирается отдельно; диагностические
строки из его вывода также показываются. Успешные команды сообщают время выполнения.

Обычная команда ограничена 300 секундами, импорт/копирование/экспорт — 1800:

```bash
bash bin/install.sh --wp-path /var/www/wp --timeout 600 --import-timeout 3600 --check
```

Журналы по умолчанию: `~/dtpstat-install-logs` (файл 0600).
Резервные копии: `~/dtpstat-backups` (каталог конкретного запуска 0700).
Их можно переопределить через `--log-dir` и `--backup-dir`, вне WP/wp-content.
В журнал не передаются аргументы с паролями администратора.

Ошибка команды останавливает установку с ненулевым кодом. Ctrl+C/TERM останавливают
группу дочерней команды; ошибки и прерывания не маскируются успехом.
Автоматического отката нет: в журнале указаны этап и каталог резервной копии.
Не запускайте повторный импорт поверх частичного результата: сначала восстановите
предыдущее состояние либо разберите конкретную ошибку.

Для ручного восстановления используются `database.sql`, `wp-content/`, `htaccess`
и `manifest.json` из одного каталога резервной копии. Восстановление БД и файлов
нужно делать совместно, при остановленных записях в сайт. Команду восстановления
следует составить с фактическими путями конкретного запуска. Копия не является
транзакционным snapshot БД вместе с файлами: во время установки сайт не должен
принимать параллельные изменения. Файлы копируются с режимами, но без сохранения
владельцев/групп; при восстановлении необходимо назначить владельца сайта.

## Границы

Только локальный, уже установленный одиночный WP с одинаковыми home/siteurl.
Compose, установка ядра, reset данных и multisite сюда не входят.
Ссылка wp-content/themes/dtpstat-child на theme/dtpstat-child этого проекта
поддерживается и сохраняется. Копирование темы в саму себя пропускается.
Резервная копия содержит фактические файлы темы на момент запуска, а manifest.json
сохраняет путь и цель ссылки в theme_symlink. При восстановлении нужно вернуть
файлы в каталог проекта и сохранить/восстановить ссылку отдельно.
Другие symlink в источнике или wp-content, внешние каталоги plugins/themes/uploads
пока отклоняются: резервная копия должна однозначно покрывать изменяемые файлы.
WP_CONTENT_DIR вне ABSPATH допустим, если каталоги внутри него и доступны текущему пользователю.

Ни импорт, ни проверка сайта не выполняются через HTTPS. Доступ к WordPress.org
нужен для загрузки отсутствующих языковых пакетов/тем/плагинов. HTTP-проверки
вёрстки из старого verify.sh в новом установщике не запускаются. Старый verify.sh
сохраняет прежний интерфейс и этим архивом не исправляется.

## Проверки разработки

```bash
python3 -m unittest discover -s tests -v
```

В `tests/test_installer.py` определены 26 unit-тестов: синтаксис
Bash/PHP/Python 3.8, передача аргументов, коды ошибок и тайм-ауты,
разбор диагностического JSON, проверки путей `uploads`, обработка
CDATA, Python 3.8.8 и гарантии отсутствия операций изменения в `--check`.
Дополнительно проверяется подготовка режима `--replace-content`,
включая удаление вложений через WordPress API и обработку ревизий.
Проверки реальных файлов `content/` выделены отдельно.

Тесты не заменяют интеграционную установку на копии WordPress.
Обязательное первое действие на целевом сервере — `--check`;
после него нужно проверить возможность восстановления резервной копии,
доступ к WordPress.org, выполнение импорта и страницы сайта.
