# DTPStat — пакет WordPress-сайта «Карта ДТП»

Репозиторий [dtpstat/dtpstat-wp-theme](https://github.com/dtpstat/dtpstat-wp-theme) содержит дочернюю тему `dtpstat-child` (родительская тема Neve), экспорт контента WordPress, медиафайлы с метаданными и установщик для **уже установленного одиночного WordPress**.

**Главная инструкция по установке: [INSTALLER.md](INSTALLER.md).** Связка с фронтендом карты описана в [SETUP.md](SETUP.md), а обновление только темы — в [DEPLOY.md](DEPLOY.md).

## Быстрый старт на существующем WordPress

Установщик запускается **локально на том же сервере, где доступны файлы WordPress, PHP CLI и WP-CLI**. Требуются Python ≥ 3.8, Bash, rsync, PHP с нужными расширениями, WP-CLI и `mysqldump` либо `mariadb-dump`. Лучше выполнять от владельца файлов WordPress, а не от `root`. В репозитории есть `wp-cli.phar`; альтернативно можно использовать `--wp-bin /usr/local/bin/wp`.

**Перед проверкой** скопируйте `wordpress.env.example` в проектный `.env` и укажите публичные URL — новый `--check` проверяет его и возможность сгенерировать `WP_CONTENT_DIR/dtpstat-config.php`. Конфигурация конкретного сайта не берётся из `/var/www/.env`. Подробности в [SETUP.md](SETUP.md).

Вначале **только проверка**:

```bash
cd /var/www/dtpstat-wp-theme
bash bin/install.sh \
  --wp-path /var/www/wp \
  --wp-cli-phar /var/www/dtpstat-wp-theme/wp-cli.phar \
  --check
```

`--check` не удаляет записи и не меняет файлы сайта. При этом создаются внешний lock-файл и журнал; WP-CLI загружает установленный WordPress и его плагины. Проверка не гарантирует доступности WordPress.org и успеха будущего импорта.

Для *сайта без существующего контента* повторите команду без `--check`. Если имеются только стандартные страницы WordPress, добавьте `--remove-stock-content` **и в проверку, и в установку**.

### ВНИМАНИЕ: замена контента существующего сайта

`--replace-content` удаляет записи WordPress, включая страницы, публикации, CPT, вложения, меню и таксономии; файлы медиа могут удаляться вместе с вложениями. Пользователи, подключение к БД и сторонние таблицы плагинов не сбрасываются. Перед удалением установщик создаёт резервную копию БД и `wp-content`, но **автоматического отката нет**. На время операции следует исключить изменения сайта.

Сначала проверить **тот же режим**, который планируется выполнить:

```bash
bash bin/install.sh \
  --wp-path /var/www/wp \
  --wp-cli-phar /var/www/dtpstat-wp-theme/wp-cli.phar \
  --replace-content --check
```

После проверки и подготовки восстановления запускать без `--check`. Не запускать повторную установку поверх частичного результата; использовать резервную копию и журнал. Подробности, ограничения и права доступа — [INSTALLER.md](INSTALLER.md).

## Состав

| Путь | Назначение |
|---|---|
| `bin/install.sh` | Точка входа в новый серверный установщик |
| `bin/generate-config.py`, `wordpress.env.example` | Внутренний генератор PHP-констант для `install`/`deploy` и пример проектного `.env` |
| `bin/install.py`, `bin/install-wp.php` | Проверки, резервная копия, импорт и проверка результата через WP-CLI |
| `content/export.xml` | WXR с контентом и записями вложений; при импорте вложения исключаются |
| `content/attachments.json` | ID, данные и метаданные медиа для точного восстановления |
| `content/uploads/` | Медиафайлы со всеми размерами, включая ручные кропы |
| `content/settings.json` | Эталонные настройки, версии, категории, меню и счётчики |
| `theme/dtpstat-child/` | Код дочерней темы Neve (PHP/CSS/JS, локальные шрифты и изображения) |
| `bin/verify.sh` | Отдельная *устаревшая* проверка стенда/HTTP, не вызывается новым установщиком |
| `bin/export.sh` | Экспорт **из конкретной Docker-песочницы** (по умолчанию `local-wp-1`) |
| `bin/deploy.sh`, `bin/deploy.py` | Локальный деплой темы и конфигурации; проверка, отдельный релиз, переключение symlink |
| `compose.yml`, `bin/wp.sh`, `bin/frontend-url.sh` | Вспомогательные средства прежнего Docker-стенда, не запускаются новым `install.sh` |
| `tests/` | Автоматические сценарии проверок установщика и пакета |

## Как работает новый установщик

Схема: проверка входных данных, зависимостей и цели → резервная копия БД и `wp-content` → подготовка контента → установка Neve и плагинов из `settings.json` → копирование темы и `uploads` → восстановление вложений с исходными ID → WXR без элементов `attachment` → URL/опции/категории/меню → проверка через WordPress.

Ручные кропы сохраняются копированием всего `uploads` и восстановлением метаданных; регенерация миниатюр **не** выполняется. Повторные элементы вложений в исходном WXR не импортируются: установщик удаляет все `attachment`-элементы перед импортом и сверяет **множество их ID** с `attachments.json`.

Импорт не равен полному откату к снимку или синхронизации с удалением лишних файлов. Не поддерживаются multisite, установка ядра WordPress и автоматическое восстановление после ошибки. Для смены адреса сайта используется `--url`; `home` и `siteurl` исходной установки должны совпадать.

## Обновление темы и экспорт контента

После установки обновлять тему **вместе с её PHP-конфигурацией** нужно через `bin/deploy.sh --wp-path /var/www/wp` (см. [DEPLOY.md](DEPLOY.md)). Прежде всего выполняйте тот же вызов с `--check`. Скрипт создаёт отдельный релиз темы, генерирует PHP-константы из проектного `.env` и переключает symlink; `rsync --delete` и удалённые HOST/WP_PATH больше не используются.

`bin/export.sh` — отдельная процедура обновления экспортного пакета из старой Docker-песочницы. Она **перезаписывает** `content/export.xml`, `content/attachments.json`, `content/settings.json` и `content/uploads/`. Не запускайте экспорт против рабочего сайта без подготовки и проверки источника.

## Карта и дополнительные компоненты

Карта — отдельный фронтенд: [website-frontend-mask](https://github.com/dtpstat/website-frontend-mask). API — отдельный проект: [dtpstat-map](https://github.com/dtpstat/dtpstat-map). В этом репозитории они не устанавливаются.

Адрес главной карты задаётся `DTP_MAP_URL`, карточек `/dtp/<id>/` — `DTP_FRONTEND_URL`. В WXR для карты хранится `src="about:blank"`; `front-page.php` подставляет адрес при рендеринге, в том числе для ранее сохранённого iframe. Все внешние URL и контакты определяются в **проектном** `.env` на основе [wordpress.env.example](wordpress.env.example), но WordPress **не читает `.env`**. Во время установки/деплоя `install` и `deploy` сами вызывают внутренний генератор и записывают константы, которые подключает тема. Отдельно запускать генератор на рабочем сайте не нужно. Подробности: [SETUP.md](SETUP.md).

## Разработка и проверки

```bash
python3 -m unittest discover -s tests -v
bash bin/deploy.sh --wp-path /var/www/wp --check
bash -n bin/install.sh
php -l bin/install-wp.php
```

Unit-тесты и статические проверки не заменяют проверку `--check` на целевом сервере и интеграционный прогон на тестовой копии WordPress.
